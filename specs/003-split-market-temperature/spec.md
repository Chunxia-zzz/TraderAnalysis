# Feature Specification: 市场温度按指数拆分（SPY / QQQ 独立计算与展示）

**Feature Branch**: `003-split-market-temperature`

**Created**: 2026-11-10

**Status**: Implemented & Deployed（2026-11-11）— 后端 110 项测试全绿；接口返回 SPY 70.3 / QQQ 79.4 / 温差 −9.1；
回算 2025-01-02 ~ 2026-11-09 共 930 行；全池 192 只评分与变更前逐只一致；前端三视图走查无报错。
已上线：后端 `f20fe4b` / 前端 `c42a996`，线上 `/market-temperature` 三视图实测通过、0 控制台错误。
⚠️ 上线时补做了一步：`market_temp_split` 是新表，**部署代码不会带数据**，必须 `scp` 同步一次 DB。

**Input**: User description: "当前系统里面美股大盘的温度，其实是合并了标普（SPY）和纳斯达克（QQQ）的温度吧。最近几个月标普一直强于纳指，所以我想将这两个的温度分开展示、单独计算。"

## 背景

现状是**结构性合并**，不是简单相加：

- `market_scorer` 的三个维度（日线技术面 50% / 周线技术面 35% / 价格位置 15%）内部，各自把 SPY 的 3 项子分与 QQQ 的 3 项子分做**算术平均**
- 即两个指数在**每一个维度上都各占 50%**，综合温度等于两个指数的等权平均
- 后果：当一个指数深度超卖、另一个尚未超卖时，合并值永远落在中间，**分化被抹平**。当前无法回答「标普和纳指谁更恐慌」「这轮分化持续了多久」

已验证的分解关系（2026-11-09 实测，非虚构）：

| 口径 | 综合 | 日线 | 周线 | 价格位置 | 距 ATH |
|---|---|---|---|---|---|
| SPY | 70.3 | 75.0 | 81.9 | 27.8 | −3.7% |
| QQQ | 79.4 | 77.5 | 92.7 | 54.7 | −10.9% |
| 合并（现状） | 74.9 | 76.2 | 87.3 | 41.3 | — |

70.3 与 79.4 的平均值 74.85 与合并值 74.9 一致（四舍五入差异）。**说明拆分是对既有口径的信息展开，不引入新的计算逻辑**；差异集中在「价格位置」一个维度，正是「标普强于纳指」的量化表达。

库中 `market_score` 现有 956 行合并值（2022-09-30 起），以 `date` 为唯一键，**在结构上无法同时容纳两个指数**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 温度页分开展示两个指数 (Priority: P1)

打开市场温度页，看到 SPY 与 QQQ 两张独立的温度卡，各自显示综合分、市场状态、三个维度的分数与权重、以及该指数的关键指标（指数点位、日线 RSI、周线 RSI、距 ATH 回撤、MA200 偏离）。页面上不再有「合并温度」这个主数值。

**Why this priority**: 这是用户提出本次需求的直接动机——要看分化，而不是看平均。

**Independent Test**: 打开 `/market-temperature`，确认存在 SPY / QQQ 两张卡、各自数值与接口返回一致；确认页面无「合并温度」主分数字段；控制台无报错。

**Acceptance Scenarios**:

1. **Given** 当日两个指数均有完整日线与周线数据，**When** 打开温度页，**Then** 两张卡各自显示综合分、状态文案、建议动作，且数值与 `GET /api/market-temperature` 一致
2. **Given** 两张卡同时存在，**When** 展开任一张的维度拆解，**Then** 显示该指数自己的日线 / 周线 / 价格位置三项分数，不出现另一指数的子项
3. **Given** 页面加载完成，**When** 检索页面文案，**Then** 不存在把两个指数混在一起描述的「大盘温度」单一数值

---

### User Story 2 - 各自给出建议仓位，不再有单一建议 (Priority: P1)

每个指数按自己的温度独立映射出建议仓位与操作建议；系统不再输出一个「全局唯一」的建议仓位。用户看到的两个仓位建议可以不同，由用户自己判断如何使用。

**Why this priority**: 用户已明确选择「各自给各自仓位」。若仍保留一个单一建议，拆分只停留在展示层，不改变决策输入。

**Independent Test**: 请求 `GET /api/market-temperature`，确认每个指数对象各自含 `target_position_pct` 与 `action_suggestion`；确认响应顶层不再有单一的 `target_position_pct`。

**Acceptance Scenarios**:

1. **Given** 两个指数温度不同，**When** 读取接口，**Then** 两个 `target_position_pct` 可以不同，且各自落在既有的仓位映射区间内
2. **Given** 任一指数温度升高，**When** 重新计算，**Then** 该指数的建议仓位单调不降（口径不反转）
3. **Given** 响应结构，**When** 前端或其他消费方读取，**Then** 不存在「全局建议仓位」字段被误当作组合闸门使用

---

### User Story 3 - 温差指标与趋势 (Priority: P1)

系统提供「温差 = SPY 温度 − QQQ 温度」这一显式指标，并给出自 **2025-01-01** 起至今的温差时间序列。温差为负表示标普温度更低（标普相对更强、更不超卖），为正表示纳指温度更低（纳指相对更强）。

**Why this priority**: 用户要回答的是「标普强于纳指多久了」，单看两张卡无法回答；温差序列才是这个问题的直接答案。

**Independent Test**: 请求温差历史接口，确认返回的首个日期不早于 2025-01-01、末个日期等于最新温度日期；把任一天的 SPY 与 QQQ 分数相减，结果与温差序列一致。

**Acceptance Scenarios**:

1. **Given** 2025-01-01 之后有 N 个交易日，**When** 请求温差趋势，**Then** 返回不超过 N 个点，且每个点的温差 = 当日 SPY 分 − 当日 QQQ 分（容差 ±0.2，来自舍入）
2. **Given** 请求趋势，**When** 指定「全部」区间，**Then** 最早日期不早于 2025-01-01；不存在 2024-12-31 及更早的数据点
3. **Given** 温差为负值，**When** 页面展示，**Then** 文案明确说明「标普相对更强」，不能只给一个带符号的数字

---

### User Story 4 - 日更自动产出两个温度 (Priority: P1)

每日行情更新后，系统自动为两个指数各算一次温度并落库，与现有日更流程串在一起，不需要额外手工步骤。同一数据日重复执行结果一致（幂等）。

**Why this priority**: 拆分温度若不能随日更自动更新，第二天就会变成陈旧数据，比不做更危险。

**Independent Test**: 连续两次执行 temperature 步骤，确认同一日期的两行数据完全一致、行数不翻倍；确认最新的两行日期等于最新 K 线日期。

**Acceptance Scenarios**:

1. **Given** 已执行完行情更新，**When** 执行温度计算，**Then** 两个指数各写入一行该数据日的记录
2. **Given** 同一数据日已存在记录，**When** 再次执行温度计算，**Then** 覆盖而非新增，总行数不变
3. **Given** 盘中运行（当日 K 线未定稿），**When** 计算温度，**Then** 数据日停在最近一个已收盘交易日，与现有 K 线收盘守卫行为一致

---

### User Story 5 - 合并值退役，历史冻结保留 (Priority: P2)

`market_score` 表中的 956 行合并历史**不删除、不改写**，只是不再新增；文档明确标注「合并口径已于某日退役，历史仅作追溯」。新口径数据独立存放，与历史合并值互不覆盖。

**Why this priority**: 删数据不可逆，且合并序列是「拆分前后是否等价」的唯一对照物；但继续写入合并值会让两套口径长期并存、互相矛盾。

**Independent Test**: 变更前后对比 `SELECT COUNT(*), MIN(date), MAX(date) FROM market_score`，三值完全一致；变更后新增日期的数据只出现在拆分表中。

**Acceptance Scenarios**:

1. **Given** 变更前 `market_score` 有 956 行，**When** 变更后再次统计，**Then** 行数与首末日期完全一致
2. **Given** 变更后的某交易日，**When** 查询 `market_score`，**Then** 该日无新增行
3. **Given** 查阅文档，**When** 想知道合并值现状，**Then** 能找到「已退役、冻结保留、不再更新」的明确说明

---

### User Story 6 - 接口与文档同步为真 (Priority: P2)

温度相关接口的返回结构、字段语义、历史端点与新端点全部写入 `docs/reference/api.md`；温度模块文档、README、CHANGELOG 同步更新；文档不得保留「全局唯一建议仓位」这类已不成立的描述。

**Why this priority**: 宪法原则 V 要求文档与代码同时为真；接口结构变了而文档不动，下一个接手的人会按旧契约写代码。

**Independent Test**: 按 `docs/reference/api.md` 的字段表逐项对照真实响应，无多余字段、无缺失字段；`skills/doc-code-consistency-audit` 可复现通过。

**Acceptance Scenarios**:

1. **Given** 新接口，**When** 对照 `api.md`，**Then** 每个字段的语义、单位、取值范围均有描述
2. **Given** 已退役的字段，**When** 检索文档，**Then** 有明确的退役标注与替代字段指向，不是静默消失

---

### Edge Cases

- **单指数数据缺失**：某指数日线或周线为空时，该指数温度标记为「数据不足」，另一指数照常输出，**不得**因一侧缺失而整体失败或返回中性分冒充真实值。
- **周线未定稿**：周五收盘前，本周周线不参与计算（沿用现有 `filter_week_closed` 规则），两个指数同一天必须用同一套「已定稿周线」判定，不能一个用一个不用。
- **2025-01-01 之前**：温差趋势接口对该区间之外的数据**不返回**，且不自动向前扩展；请求更早区间应返回空列表而不是报错或静默补算。
- **日期无温度记录**：某交易日缺失（例如多日未跑日更后补数不完整）时，温差序列跳过该日，不做插值，避免用假点连出假趋势。
- **前端旧缓存**：Vite 旧 chunk 仍按旧结构解析响应会白屏；验证时必须强刷。
- **极端层标记**：`extreme_triggered` / `leverage_tool` 现由合并值判定，拆开后必须按各指数分别判定；不得把合并期的极端结论套用到单个指数上。
- **既有消费方**：日报生成、`/api/allocation`、任何把 `target_position_pct` 当组合闸门的代码路径，均需确认不再依赖单一全局值。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为 SPY 与 QQQ 分别计算三维温度（日线技术面 50% / 周线技术面 35% / 价格位置 15%），权重与现有口径一致
- **FR-002**: 两个指数 MUST 共用同一套阈值（ATH 回撤满分线、MA200 偏离映射区间），以保证两个分数可跨指数直接比较、温差有意义
- **FR-003**: 拆分后的两指数温度 MUST 可验证地等于既有合并计算的分项平均（同一数据日、容差 ±0.5），证明口径未被改变
- **FR-004**: 每个指数 MUST 独立输出 `composite_score`、`market_status`、`action_suggestion`、`target_position_pct`、`extreme_triggered`、`extreme_level`、`leverage_tool`
- **FR-005**: 接口 MUST NOT 再输出单一的全局 `composite_score` 与全局 `target_position_pct`
- **FR-006**: 系统 MUST 提供温差指标（SPY 温度 − QQQ 温度）及其自 2025-01-01 起的时间序列
- **FR-007**: 温差序列 MUST 不包含 2025-01-01 之前的日期；缺失交易日 MUST 跳过而非插值
- **FR-008**: 温度计算 MUST 幂等：同一数据日重复执行覆盖写，不产生重复行
- **FR-009**: 日更流程中的温度步骤 MUST 一次产出两个指数的记录，不增加额外手工步骤
- **FR-010**: `market_score` 表的既有 956 行合并值 MUST 保持原样，不执行 `DELETE` / `UPDATE` / 迁移；变更后 MUST 不再向该表写入新行
- **FR-011**: 前端温度页 MUST 以两张独立卡展示两个指数，不再展示合并温度主数值
- **FR-012**: 前端 MUST 展示温差趋势，并明确标注正负值的方向含义
- **FR-013**: 某个指数数据不足时 MUST 只降级该指数，另一指数与页面其余部分不受影响
- **FR-014**: 文档 MUST 更新为「温度已按指数拆分、合并值退役冻结」，并同步接口字段表、模块文档、README 与 CHANGELOG
- **FR-015**: 个股评分 `total_score`、利弗莫尔关键点、信号扫描、持仓与目标仓位计算 MUST 不受本次变更影响
- **FR-016**: 个股评分的「大盘恐慌加成」输入 MUST 继续等价于拆分前的合并温度（即两指数温度的算术平均），使同一数据日的 `total_score` 与变更前一致（容差 ±0.5）；不得改用单一指数作为加成输入

### Key Entities

- **指数温度记录**：某数据日 + 某指数（SPY/QQQ）的唯一一条温度结果，含综合分、三维分数、状态文案、建议动作、建议仓位、极端层标记、关键指标快照。
- **温差序列点**：某数据日的 SPY 温度减 QQQ 温度，用于判断两者相对强弱及持续性。
- **合并温度历史**：`market_score` 中 2022-09-30 起的 956 行，已退役、只读、仅供追溯与等价性核对。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一数据日的 `(SPY 温度 + QQQ 温度) / 2` 与拆分前该日合并温度之差 **≤ 0.5 分**（抽查 2025-01-01 后任意 5 个交易日）
- **SC-002**: 2025-01-01 至今的温差序列点数 **等于该区间交易日数**（缺失交易日除外），且首点日期不早于 2025-01-01
- **SC-003**: `market_score` 行数在变更前后均为 **956**，首末日期不变
- **SC-004**: 同一数据日连续执行两次温度计算，拆分表该日行数 **恒为 2**（每个指数一行），不翻倍
- **SC-005**: `pytest -q` 全绿，失败数 **0**；新增测试覆盖单指数评分、温差、幂等、数据不足降级
- **SC-006**: 温度页人工走查：两张卡、温差图、无合并主数值、无空状态、无控制台异常
- **SC-007**: `docs/reference/api.md` 与新接口实测响应逐字段一致，无未文档化字段
- **SC-008**: 抽查 3 个交易日，变更后重算的 `total_score` 与变更前该日记录一致（容差 ±0.5），确认恐慌加成未失血

## Assumptions

- 用户已确认「拆分取代合并」：主视图不再保留合并温度，也不再输出单一建议仓位。
- 用户已确认两个指数**共用一套阈值**，接受 QQQ 因波动更大而系统性偏高；两分数可比、温差可解读，优先于单指数绝对精度。
- 用户已确认温差历史**只回算 2025-01-01 起**，更早不做处理；2024 年及以前不补算、不迁移。
- 合并温度历史保留在同一库同一表，不迁移到归档库；因此它只是不再增长，而非被清理。
- 「温差」的符号约定为 SPY − QQQ，负值代表标普相对更强；这是展示语义，不构成交易建议。
- 两个指数都是美股标的，共用美股交易日历与收盘规则，无需引入新的市场时钟逻辑。
